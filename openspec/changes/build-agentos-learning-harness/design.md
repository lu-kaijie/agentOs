## Context

当前仓库还处在提案阶段，尚未实现真正的 agent runtime 或 harness。你的目标不是直接拿到一个成品，而是通过亲手搭建一个类似 coding agent 的系统，逐步理解 agent loop、工具调用、状态编排以及 harness 的职责边界。与此同时，这个项目还要承担 LangChain 和 LangGraph 的学习任务，因此早期架构必须足够清晰，能直接看出图状态、节点切换、执行流程和运行时边界。

这带来三个明确约束。第一，实施过程必须按里程碑推进，每一步都要足够小，能够独立完成、复查、打 tag 和发布。第二，初始架构优先保证“看得懂”，而不是一开始追求功能齐全，因此 Python 结构、依赖策略以及 harness 分层都要为后续扩展留空间，同时不能把核心机制藏在过深的抽象里。第三，项目最终目标不能只是课程式 demo，而应逐步具备实际可用性和一定复杂度，因此前期设计就需要为更丰富的 runtime 能力和框架特性留出演进路径。

## Goals / Non-Goals

**Goals:**

- 制定一套能“边做边学”的实现方案，让项目按层次逐步搭起 coding-agent 风格系统。
- 首个 runtime 直接使用 LangChain 和 LangGraph，让项目从一开始就覆盖提示词、工具、图状态和执行编排。
- 在后续里程碑中系统覆盖更多 LangChain/LangGraph 用法，让你在项目完成后对这两个框架有较完整的实践理解，而不是只停留在基础 graph demo。
- 建立本地开发 harness，并明确命令执行边界，为未来加入 sandbox、日志和审批机制预留扩展点。
- 逐步补齐 agent 控制面，包括任务持久化、上下文治理、知识装载、后台执行、并行隔离和多 agent 协作。
- 规范 GitHub 公开仓库所需的基础文件、依赖锁定、环境说明和里程碑 tag 流程。
- 保证每个里程碑都能独立停下、独立发布、独立理解。
- 让项目在逐步实现后具备真实可用性，而不是只支持单条 happy path 演示。

**Non-Goals:**

- 第一阶段就复刻成熟 coding agent 的全部能力。
- 在最初几个里程碑中设计生产级 sandbox、远程执行器或多 agent 调度系统。
- 这一阶段解决长期部署、云端托管或分布式执行问题。
- 在真正开始实现前就把所有架构细节一次性锁死。

## Decisions

### 1. 按里程碑切片推进，而不是一次性端到端实现

项目将被拆成一系列检查点，每个检查点只有一个主要学习目标，并且仓库在该点上应处于可发布状态。

理由：
- 这符合你“要一步一步带着实现”的核心诉求。
- 每完成一个检查点后都可以回头校正设计，降低前期判断失误带来的返工。
- Git tag 会更有意义，每个 tag 都对应一个可复现、可讲解的学习节点。

备选方案：
- 先把完整架构做出来，再补解释文档。否决，因为它优化的是速度，不是理解。
- 只分成“初始化”和“正式实现”两阶段。否决，因为学习面仍然过宽。

### 2. 使用项目相关命名的本地虚拟环境 `.venv-agentos` 和精确版本 requirements

初始环境将使用仓库本地虚拟环境 `.venv-agentos`，依赖从精确版本锁定的 requirements 文件安装。必要时可拆分运行时依赖与开发测试依赖。

理由：
- 直接满足你对“虚拟环境先建好、依赖装进虚拟环境、版本限定明确”的要求。
- `.venv-agentos` 这样的命名比通用 `.venv` 更容易在多项目环境下识别。
- 精确版本锁定可以保证每个 milestone tag 都可重复安装和复现。

备选方案：
- 使用 Poetry 或 uv。第一阶段不采用，因为会额外引入工具链学习成本，分散对 agent 核心机制的注意力。
- 使用宽松版本范围。否决，因为不符合版本锁定要求。

### 3. 尽早拆分 `agent runtime`、`harness` 和 `project scaffolding`

实现上应从一开始区分三类职责：
- runtime：图状态、提示词、工具绑定、步骤推进
- harness：命令执行、输入输出边界、审批钩子、日志/转录
- scaffolding：CLI 入口、配置、仓库文档、测试

理由：
- 这更接近真实 coding agent 系统的可维护结构。
- 教学价值更高，因为职责边界是显性的。
- 后续若替换执行器、增加审批或加入更多 runtime 逻辑，不需要推倒重来。

备选方案：
- 用一个 `main.py` 原型先跑通。否决，因为它对 harness 边界的教学价值太低，而且很快会变成一次性代码。

### 4. LangGraph 从一个最小但清晰的图开始

第一个 agent runtime 应至少展示以下内容：
- 输入任务状态
- 模型决策步骤
- 工具执行步骤
- 循环或终止条件

理由：
- 这样能最早暴露 LangGraph 的核心心智模型。
- 后续扩展 memory、retry、plan/act 拆分时有自然演进路径。
- 与你希望系统性学习 LangChain/LangGraph 的目标一致。

备选方案：
- 先用纯 LangChain chain。否决，因为会推迟你最想学的图编排概念。
- 把 LangGraph 再封装一层隐藏起来。否决，因为初期实现应保持可读、可研究。

### 5. 从一开始就为“进阶框架能力”预留演进路线

虽然第一个 runtime 会保持最小可讲解结构，但设计上必须明确后续将逐步覆盖更多 LangChain/LangGraph 能力，例如：
- structured output 与 schema 约束
- prompt 模板与消息状态管理
- tool binding 与工具结果回填
- 条件分支与多步路由
- memory 或 persistence
- human-in-the-loop 审批节点
- tracing、调试、评估或运行观测

理由：
- 你的目标是学会框架，而不是只记住一个最小示例。
- 更复杂、可用的项目天然能逼出更多框架能力的真实使用场景。
- 先在设计中给出路线，可以避免后续每次扩展都偏向临时拼接。

备选方案：
- 等基础版本完成后再决定是否扩展框架用法。否决，因为这样容易导致项目结构只适配最小 demo。

### 6. GitHub 发布规范从第一步开始纳入流程

每个里程碑都应定义当前阶段需要具备的说明文件、忽略规则、启动文档和打 tag 说明，而不是等功能做完再补。

理由：
- 你明确希望边做边上传 GitHub。
- 持续保持仓库可发布，比后期集中补规范成本更低。

备选方案：
- 等 runtime 能跑了再整理仓库。否决，因为会削弱里程碑纪律，也会增加后期清理成本。

### 7. 任务系统应尽早从“会话内计划”升级为“磁盘持久化控制面”

项目不能只依赖一次对话里的 Todo 列表。较早阶段就应引入能落盘的任务模型，至少支持任务状态、依赖关系和恢复。

理由：
- 可用系统需要跨会话持续工作，不能把计划只寄托在上下文窗口里。
- 任务图是后续后台执行、委派、并行工作和恢复能力的共同骨架。
- 这也能自然承接 LangGraph 的状态与流程控制，而不是把一切都塞进消息历史。

备选方案：
- 只保留内存态 Todo。否决，因为它无法支撑长流程与恢复能力。

### 8. 上下文管理和知识装载必须成为一等设计对象

项目后续如果要做复杂任务，消息历史和工具输出一定会膨胀，因此必须预留上下文压缩与按需知识加载机制。

理由：
- 真实 agent 系统不会永远停留在短会话。
- LangChain/LangGraph 的很多能力只有放进长流程和状态治理里，学习价值才足够高。
- 按需装载知识或技能，比一开始把所有规则塞进 system prompt 更符合可维护性。

备选方案：
- 初期忽略上下文问题。否决，因为这会让后续复杂度提升时出现结构性返工。

### 9. 后台执行与隔离执行上下文是“可用性”而非“锦上添花”

如果系统要逐步变得可用，就不能要求所有长耗时操作都阻塞主循环，也不能假设所有任务都永远共享同一工作目录。

理由：
- 长命令、测试、安装、构建等任务是 coding agent 的常见场景。
- 并行工作如果没有隔离执行面，后续很容易被目录污染和状态冲突拖垮。
- 这类机制能显著增加项目复杂度和实战价值，同时也引出更多框架与工程模式。

备选方案：
- 只做同步串行执行。否决，因为过于接近 demo。

### 10. 多 agent 协作必须建立在可观察的协调状态之上

后续如果要引入多 agent 或角色化执行，不应直接追求“神秘自治”，而要先把委派边界、状态追踪和结果回流机制设计清楚。

理由：
- 这更容易教学，也更容易调试。
- 它能保证复杂度增加时系统仍然可理解。
- 这也为 LangGraph 中更复杂的分支、子图或角色化流程提供实践土壤。

备选方案：
- 直接做黑盒式并发多 agent。否决，因为学习价值低，维护风险高。

## Risks / Trade-offs

- [以学习优先会降低短期功能推进速度] → 缓解：把每个里程碑压缩到一个明确结果，不在单步里塞太多目标。
- [精确版本锁定会随着时间老化] → 缓解：只在里程碑边界升级依赖，并记录升级原因。
- [LangGraph 概念对起步阶段有一定门槛] → 缓解：首个图保持最小化，先不引入复杂分支、持久化和高级记忆能力。
- [过早设计 harness 边界可能显得超前] → 缓解：先定义接口和最小实现，不提前做完整 sandbox 基础设施。
- [追求更高复杂度会让项目失控] → 缓解：复杂度按里程碑递增，每一阶段只引入 1 到 2 个新的框架能力点。
- [任务系统、并行执行和多 agent 过早叠加会让调试难度飙升] → 缓解：先做单 agent + 持久化任务图，再逐步引入后台执行、隔离上下文和委派。
- [每阶段打 tag 会增加流程成本] → 缓解：只在里程碑完成时打 tag，不为零碎提交增加额外负担。

## Migration Plan

当前没有旧系统需要迁移，因此实施方式以“逐步新增”为主：

1. 初始化仓库公开文件、`.venv-agentos` 工作流和精确版本 requirements。
2. 建立最小 Python 包结构和 CLI 入口。
3. 加入第一版 harness 执行器抽象和本地命令执行器。
4. 加入第一版 LangGraph runtime，跑通一个最简单的工具循环。
5. 加入持久化任务图，为复杂工作流和恢复能力建立控制面。
6. 逐步扩展 structured output、条件路由、状态持久化、知识加载、审批节点和观测能力等进阶框架用法。
7. 加入后台执行、隔离工作区和多 agent 协作等更高复杂度能力。
8. 为每个阶段补充测试、里程碑说明和 tag 发布说明。

如果某一步需要回退，当前阶段最直接的方式是回退到上一个稳定 milestone tag。
