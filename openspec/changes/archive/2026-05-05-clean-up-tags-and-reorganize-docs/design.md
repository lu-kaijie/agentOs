## Context

`agentOs` 的主要产品能力已经基本收敛，但仓库仍然处于“功能先完成、资料后补齐”的状态。当前存在两个明显问题：

1. 历史 tag 与实际里程碑存在重复指向、缺失版本和说明不一致的问题，影响回溯和演示。
2. 文档入口分散，`README.md` 过载，`docs/` 下的文档按时间堆积，缺少稳定的信息架构。

这次 change 不新增产品功能，而是做仓库级收尾治理。由于会同时修改 Git 版本历史映射、README 导航和大批文档文件，这属于跨模块的整理工作，适合先用 design 固定原则，避免实施时边改边变。

约束：
- 面向中文使用者，文档默认中文。
- 该仓库当前为单用户维护，可以接受修正历史 tag，但仍要按“先映射、再修改、再核对”的顺序执行。
- 不触碰产品主功能实现，不借这次 change 顺手做新的 runtime 能力。

## Goals / Non-Goals

**Goals:**
- 建立一份明确的 tag 到 commit、tag 到 milestone、tag 到能力的映射关系。
- 修复错误或重复的历史 tag，补齐缺失 tag，并把最终结果写入版本记录文档。
- 把 `README.md` 重写为仓库首页，承担导航和总览职责。
- 将现有文档重组为稳定目录，覆盖产品介绍、快速使用、迭代记录、学习路径、源码带读、面试准备等用途。
- 在实施完成后执行至少两轮核对，确认 tag 映射、文档导航、文件迁移和链接关系都正确。

**Non-Goals:**
- 不新增 agent runtime、tool runtime、context runtime 的产品能力。
- 不对历史代码做功能性回滚或重写，只修正文档和版本标识。
- 不承诺把每个历史 commit 都补成完美的一一对应发布，只要求当前标签体系清晰、自洽、可追溯。

## Decisions

### 1. 把本次 change 分成两个能力域：版本治理和文档治理

原因：
- 这两部分都属于“仓库收尾工程”，但验收方式不同。
- 版本治理关注 tag、commit、milestone 的一致性；文档治理关注目录结构、导航和内容边界。

备选方案：
- 只改文档，不改 tag。
  - 放弃原因：用户已经明确接受修正 git 历史标记；如果 tag 继续错误，版本文档本身也会失真。
- 一次性按 commit 重写全部发布历史。
  - 放弃原因：成本过高，且对单用户仓库没有必要。

### 2. README 只做首页，不再承担全部说明

原因：
- 当前 README 同时承担产品介绍、使用说明、开发说明、里程碑说明、学习材料，导致维护困难。
- 首页式 README 更适合作为 GitHub 首屏入口，其余细节应下沉到 `docs/`。

备选方案：
- 保持 README 大而全。
  - 放弃原因：后续越迭代越难维护，用户也很难快速找到目标材料。

### 3. 文档采用按“用途”分区，而不是继续按时间堆叠

目标目录方向：
- `docs/product/`: 产品介绍、快速上手、使用与配置
- `docs/roadmap/`: 版本记录、tag/milestone 映射、发布规范
- `docs/learn/`: 项目是如何一步一步做出来的
- `docs/architecture/`: 核心模块源码带读与执行链路
- `docs/interview/`: 面试视角的知识点与取舍说明

原因：
- 按用途组织更稳定，后续新增内容不会继续污染根目录。
- 同一类读者只需要一个入口，例如使用者、学习者、面试者。

备选方案：
- 沿用当前 `docs/milestones/*.md` 加零散根文档。
  - 放弃原因：信息查找成本高，后续难扩展。

### 4. Tag 修复采用“先生成映射表，再执行重写，再双重复核”

执行原则：
- 先基于现有 commit 历史和 milestone 文档生成目标映射表。
- 再执行 tag 删除、重建、补齐。
- 最后做两轮核对：
  - 第一轮核对 git 结果：每个 tag 指向、缺失补齐、重复解除。
  - 第二轮核对文档结果：版本记录、README 链接、里程碑说明与 git 实际一致。

原因：
- tag 修改不可随意拍脑袋，必须先有明确目标表。
- 用户特别要求“改完之后多核对两次”，这里将其固化为实施要求。

备选方案：
- 直接按感觉移动 tag。
  - 放弃原因：极易再次引入错位。

### 5. 历史文档以迁移和重组为主，不强求全部保留原位

原因：
- 当前部分文件名带有明显阶段性，例如 `second-change-milestones.md`、`third-change-milestones.md`。
- 为了形成产品化文档体系，允许将内容合并、拆分、迁移，并用新文档承接。

备选方案：
- 所有旧文档保留不动，只新增索引页。
  - 放弃原因：会保留大量重复内容，继续制造双份真相。

## Risks / Trade-offs

- [Risk] 历史 tag 重写后与用户本地已有引用不一致
  → Mitigation：在实施文档中给出修正命令和最终映射表；由于当前是单用户仓库，可接受。

- [Risk] 文档迁移后旧链接失效
  → Mitigation：重写 README 导航，并做第二轮链接核对。

- [Risk] 新文档体系太大，短期维护成本上升
  → Mitigation：先建立清晰骨架和高价值文档，避免无边界扩写。

- [Risk] 版本映射与实际提交内容仍存在少量“阶段边界模糊”
  → Mitigation：以“可解释、可追溯、自洽”为优先目标，而不是追求绝对完美的历史发布学术还原。

## Migration Plan

1. 盘点当前 tag、commit、milestone 文档和 README/`docs/` 现状。
2. 产出目标 tag 映射与目标文档目录结构。
3. 重写 README，并迁移/新建文档到目标结构。
4. 执行 tag 修复与缺失 tag 补齐。
5. 完成两轮核对：
   - 第一轮：git tag 与映射表核对。
   - 第二轮：文档结构、导航、链接、版本说明核对。

若中途发现目标映射判断有误，可先停止 tag 重写，仅保留文档改动；tag 修改始终放在映射确认之后执行。

## Open Questions

- `v0.28.0` 应该单独对应哪个 commit，还是与某次文档/配置整理合并定义，需要在实施时最终确认。
- 历史 milestone 文档是否全部保留副本，还是只保留整理后的统一版本记录，需要根据迁移后的可读性决定。
